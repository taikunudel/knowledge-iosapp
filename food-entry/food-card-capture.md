# Food Card Capture (No Chat Window) + Food-Log Date Swipe + Trend Highlight

*Established 2026-06-20. Three user requests, each recorded below. Two REVERSE long-locked rules (the AI chat window; the disabled food-log date swipe) — by explicit, recent user instruction, so the newer instruction wins (Meta Rule). The superseded sections are annotated in place. Build-verified (`BUILD SUCCEEDED`, iPhone 17 Pro sim) + the food card was screenshot-verified.*

### The AI chat WINDOW is removed — sending a food = blur + ONE floating food card
User verbatim: *"i do not want the ai chat window, i just when i type and send a food entry, there is a no a panel at all, just background be blurred, and the when the answer is ready, show as a one nicely design food card, and let user to decide to add it or no."* Scope (user, 2026-06-20): *"Remove it entirely"* — there is **no chat conversation anywhere**; every send is a food analysis → card. General Q&A is gone.

- **Flow:** the global composer's send (text) and image-pick now call **`SharedInputBar.onCaptureFood(text:imageData:)`** → **`ContentView.beginFoodCapture(text:imageData:)`**, which sets a small state machine (`FoodCapturePhase` = `.idle`/`.analyzing`/`.result`/`.error`) and runs `aiManager.analyzeNutrition(...)` in a `Task`. While `.analyzing`/`.result`/`.error`, **`ContentView.foodCaptureOverlay`** shows a **frosted `.ultraThinMaterial` full-screen backdrop** (this is "background be blurred") + a card: a loading card, then the result **`CapturedFoodCard`**, or an error card with Retry/Dismiss.
- **`CapturedFoodCard`** (file-scope in [Nutritionist/ContentView.swift](Nutritionist/ContentView.swift)) is the "one nicely designed food card": image/emoji + name, flame kcal + heart health, color-coded macro chips (Carbs/Protein/Fat/Fiber), reasoning (3 lines), a **meal segmented picker (user ALWAYS picks the meal)**, a "Today / <weekday, date>" label showing the day it logs to, **`Add to <Meal>`** (primary) + **`Not now`** (dismiss) + **`Save to Library`**, and a "✨ <model>" attribution. Opaque `systemBackground` surface (it's a modal the user must read — not glass-on-glass).
- **Add → logs to the FOCUSED day, not today.** `commitCapturedFood()` inserts a `FoodEntry(date: captureTargetDate, mealCategory: foodCaptureMeal, …)` (do/catch + rollback). User verbatim: *"if i am on yesterday and i chat to aadd food, it should add to yesterday, not always today."* `captureTargetDate = (selectedTab == 0 ? selectedDate : Date())`.
- **Dismiss** = the `Not now` button OR tapping the frosted backdrop. A `foodCaptureToken` (UUID) invalidates a late/stale analysis result if the user dismissed the loading state before it returned.
- **Under the hood the AI result still persists as a `ChatMessage`** (so `Save to Library`/Past Food keep working via `sourceMessageID`) — there's just no chat UI showing it.
- **`AIChatView` is now DEAD code** (no longer presented; the `.sheet(isPresented: $isChatPresented)` + `isChatPresented` state + the `.switchToChatFocused`/`.switchToChatWithImage` posts are all removed). It's left compiled-but-unused (like `drawerRoot`); **don't reintroduce a chat sheet/screen.** This **supersedes the entire "AI Chat Overlay — Native Sheet With Detents" section** (annotated there) and the v6 "send presents the chat overlay" behavior.
- **Empty-state "Add food" pill** (`FoodEntriesCardContent`, no food on the day) now posts **`.focusHomeComposer`** → `UnifiedChatInputBar` focuses its field (was `isChatPresented = true`). There's no chat to open; the user types a meal.
- **New `-UITestCaptureCard` DEBUG launch arg** shows the floating card on launch with sample data (so it can be screenshot without a live AI call) — added to the DEBUG harness list.

### Food-log DATE SWIPE re-enabled (REVERSES the "permanently disabled" lock)
User verbatim: *"add a swipeing effect on the food entry, left to right to swicth date."* This **reverses** the locked *"horizontal date-swipe on the Today food log is permanently disabled"* rule (annotated in "Food Log Rendering"). Confirmed OK because **there is no drawer in the current design** (user 2026-06-20: *"there is no drawer design at all on the current version"* — `useDesignNav = true`, so `drawerRoot`/`DrawerPanGestureModifier` aren't in the active path, freeing horizontal swipes).

- **Implementation:** the flat-paper food-log surface (`homePinnedCardSurface` in [Nutritionist/Views/TodayView.swift](Nutritionist/Views/TodayView.swift)) is wrapped with `.id(selectedDayKey)` + `.transition(homeDateSwipeTransition)` + `.offset(x: homeDateSwipeDX)` + **`HomeDateSwipeModifier`** — a UIKit **horizontal** axis-locked pan (`HomeDateSwipeAxisPanGestureRecognizer`, iOS 26) that is the **mirror of `TodayCardAxisPanGestureRecognizer`**: a 10 pt touch-slop decides horizontal-vs-vertical; **horizontal → begins** (switch date), **vertical → fails** so the flat-paper vertical ScrollView scrolls. `shouldBeRequiredToFailBy` returns true for the `UIScrollView` pan so the page waits for the swipe's slop decision (same pattern as the drawer/card recognizers — see "Global Swipe"). iOS 17/18 fallback is a plain `.gesture(DragGesture)`.
- **Direction:** swipe **right → previous day**, swipe **left → next day** (capped at today — no logging into the future). Commit uses the projected end translation (a flick counts). The day change animates a slide (`.move` transition) keyed on `selectedDayKey`.
- **Don't** attach a horizontal gesture that claims taps (use the slop recognizer); **don't** re-add the old `calendarCardSwipeEnabled`/Settings toggle (the swipe is just on by design now).

### Trend bars — selected highlight STAYS PUT when paging weeks
User verbatim: *"when swiping on the 7 day bars on the today's view, the currently highlight date stay unchanged instead of they switch to a date in the current 7 days."* (User chose: *"No highlight unless selected day is shown."*)

- **`TodayView.selectedTrendIndex(_:)` now returns `Int?`** — `nil` when `selectedDate` isn't in *this* week's 7-day window (it no longer defaults to the last bar). **`CalorieTrend.selectedIndex` is now `Int?`**: when nil, NO bar is emphasized/highlighted (all bars full-opacity, no dot, no rounded background), so paging the trend `TabView` to a previous week leaves the selected day (and the food log) unchanged. Tapping a bar still selects that day (`onSelect` unchanged).

### Plumbing changes (so the above works)
- **`selectedDate` is HOISTED to `ContentView`** (`@State`, bound into `TodayView` as `@Binding`). Drives `captureTargetDate` + the composer's `libraryTargetDate`. `TodayView(selectedTab:selectedDate:)` (the `isChatPresented` binding is gone).
- **Library picker now asks for a meal + logs to the focused day.** `FoodCardLibraryView` `.picker` mode: tapping a card opens a **meal `confirmationDialog`** (`commitPick(_:meal:)`), logging to the passed `targetDate` (= `captureTargetDate`). User: *"if selected from library, let me select meal and still add to the currently highlight date, not always today."* (The `.picker`'s `mealCategory` associated value is now an ignored default.)
- **`SharedInputBar`**: `onPresentChat` → **`onCaptureFood: ((String?, Data?) -> Void)?`**; `sendFromHome` and `onImageReady` call it; the `useGeneralQA`/notification-posting paths are removed. The global composer passes `targetDate: captureTargetDate` + `onCaptureFood`.

### 2026-06-20 follow-ups — trend direction, full-date header, card portion, finger-following swipe
Four refinements after the first pass (build-verified + screenshot-verified on the iPhone 17 Pro sim):

- **Calorie-trend pages reversed — previous weeks on the LEFT, today on the right.** User: *"when swipe to the right on the calorie bar … ensure the previous dates are on the left, not on the right."* The `TabView(selection: $trendWeekPage)` `ForEach` is now **`(0...maxTrendWeeksBack).reversed()`** so pages lay out oldest-left → current-week-right; `trendWeekPage` stays `0` = current week (now the rightmost page). So today sits at the right edge and **swiping right reveals previous dates entering from the left** (a natural timeline). Don't un-reverse it. (The day order WITHIN a week — `macroSeries` oldest→newest — is unchanged.)
- **Full date header, pinned top-left of Today.** User: *"add a full date on the top left, this shows intuitively what date is highlighted."* `ContentView.todayDateHeader` (a 2-line "Today/<weekday>" + "<Month d>" label) is shown in the **top-leading overlay** (`designLeadingNavButton`, `selectedTab == 0`), so it's pinned (doesn't scroll) and updates when the trend bar is tapped or the food log is swiped to another day. It reads `ContentView.selectedDate`. Verified not to overlap the globe.
- **Portion control on the food card (`CapturedFoodCard`).** User: *"the calorie calculation … does not consider the portion, such as 10x portions or 0.5 portions … only half of this meal is eaten."* Root cause: the new capture card had **no portion control** (the old chat card did), so everything logged at 1×. Fix: a **Portion stepper (− / `N×` / +, 0.5×–10×, step 0.5)** on the card; the header kcal + macro chips show the **portion-scaled** values live (`scaledCalories`, `value * portion`), and **`commitCapturedFood` scales calories + nutrition JSON + `portionMultiplier`** by the chosen portion (new `ContentView.scaledCapturePayload(_:scale:)`, a mirror of `MessageBubble.scaledNutritionPayload`; stored JSON stays already-scaled per the "Already-Scaled Payload" rule). `ContentView.foodCapturePortion` (`@State`, reset to 1.0 each capture) is bound into the card. NOTE: the *calorie trend bar* itself already honored portion (the row's "Adjust Portion" rescales `entry.calories` + the JSON, which `macroCaloriesForDay` reads) — the gap was purely the missing control at capture time.
- **Food-log date swipe is now a 1:1 finger-following PAGER (supersedes the first pass's `.id`/`.transition` slide).** User: *"the swiping the left and right on the food entry is not very natural, the food should follow the finger very well."* The food log is a **`ZStack` of the current day + the adjacent day**, both `homePinnedCardSurface`s: the current tracks the finger 1:1 (`homeDateSwipeDX`), the neighbor (`homeDateSwipeNeighborDate` — previous on a rightward drag, next/≤today on a leftward drag) sits at `homeDateSwipeDX ± cardWidth` and slides in with the finger; `.clipped()` makes the pager window. On release the commit is **velocity-driven** (2026-06-21 — user: *"the food swiping is less natural than the calorie bar swiping, especially when swiping very quickly"*): `homeDateSwipeEnded(dx, velocity:)` commits when `dx + velocity·0.20` crosses a LOW `0.22·width` threshold OR on any flick (`|velocity| > 320`), and the commit spring's response **scales with the release speed** (`commitDateSwipeAnimation` = `remaining/speed`, clamped 0.16–0.40) so a fast flick continues fast instead of re-accelerating from a stop (approximating the native `TabView` paging the calorie bar uses). The recognizer now passes the **raw release velocity** (not a pre-projected translation). `finishHomeDateSwipe` swaps `selectedDate` + resets `dx` to 0 in a `disablesAnimations` transaction (the neighbor is already at x=0 → seamless), guarding against a mid-slide date change. Swiping left past today rubber-bands (×0.22). The UIKit `HomeDateSwipeAxisPanGestureRecognizer` is unchanged. **The food-log area FILLS the space below the trend** (user 2026-06-21: *"swiping on the area under the calorie bar should be seen as swiping the food entry … i do not have difficult swiping on empty log"*): `homeFoodLogPager` is `.frame(minHeight: foodLogFillHeight)` + `.contentShape(Rectangle())`, where `foodLogFillHeight` = viewport height − the food log's measured top (a `FoodLogTopPreferenceKey` minY in the `"todayContent"` coordinate space, loop-safe because the top is independent of the food log's own height). So the WHOLE region under the calorie bar is a swipe target, not just the small "+ Add food" pill on an empty day. The pager was extracted from `body` into `homeFoodLogPager(cardWidth:topGap:)` to keep the body type-checkable (the inline version tripped "unable to type-check this expression in reasonable time"). **The old `homeDateSwipeTransition`/`homeDateSwipeFromEdge` + the `.id(selectedDayKey)`/`.transition` on the food log are removed — don't reintroduce them.**
