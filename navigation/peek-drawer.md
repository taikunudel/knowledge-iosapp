# Navigation — Layered Peek Drawer (DrawerShell), No Tab Bar

*Established: 2026-05-20 (hamburger Menu); **superseded 2026-06-04** by the design-system DrawerShell side drawer; **peek refined 2026-06-05** to match the Claude iOS app.*

> **2026-06-04 supersession (REVERSES the "no drawer" lock).** The user asked for the side bar — verbatim: *"you havent implemented the side bar."* Top-level navigation is now the design system's **`DrawerShell`**: tapping the top-leading hamburger slides the active screen **right**, revealing a nav panel layered underneath; tapping the peeked-screen sliver closes it. This **reverses the earlier locked rule** "no slide-in side drawer / no `isDrawerOpen` state" (user verbatim *then*, 2026-05-20: "i dont need the side bar, just the liquid glass button…"). The newer direct instruction wins. The hamburger (liquid-glass circle) is **retained** — it now *toggles the drawer* instead of opening a Menu. **No bottom tab bar** (still forbidden).

> **2026-06-05 refinement (match the Claude iOS app).** The user flagged the peek as *"definitely problematic"* and pointed at the Claude app's drawer as the target ("i want it to look like the second screenshot"). Two fixes: **(1) full-fidelity peeked screen** — the working tree had layered a `Color.nutritionistRice` 0.62 scrim **and** `.saturation(0.18)` over the peeked screen, washing it into a grey/dead-looking card; both are removed, so (like Claude) the screen stays crisp + full-color, its only depth cues the soft left shadow + a gentle **30 pt** corner (was an over-rounded **52**). **(2) the nav panel now ADAPTS to the color scheme** instead of being hardcoded cream — warm-dark (`#3c3630 → #2b2620`) in the app's **default dark** mode, cream (`nutritionistRice`) in **light** mode — so the menu and the peeked screen stay tonally consistent in both modes (the old hardcoded-cream panel sat behind a near-black `.systemBackground` screen in dark mode = an ugly mismatch). **No `scale(0.86)`** — the design-system spec scaled the card down, but Claude (and now this app) keeps it full-height; **don't reintroduce the scale**, the scrim, or the desaturation. Verified by screenshot in light + dark + closed states.

> **2026-06-05 follow-up (the slide must be honest).** The first pass still had the rounded corners on the **wrong side**: user verbatim *"i want the panel to faithfully honestly slide to the right, so 1st, the corner is in the right side [wrong], 2nd the panel is truncated [wrong]."* Root cause was a SwiftUI modifier-**order** bug — `.offset` then `.clipShape` rounds the device's right edge (because `.offset` is layout-neutral, the clip is laid out at the pre-offset frame), leaving the leading edge a flat cut and an ugly mid-screen rounded truncation. **Fix: clip + shadow BEFORE the offset** (see the peek-transform bullet). Now the active screen rounds into a card and slides right with its **left corners leading** at the menu boundary, the right side running cleanly off the device edge — an honest slide. Don't reorder these three modifiers.

> **2026-06-05 follow-up #2 (full height — "exactly just horizontally move right").** The peeked card was still **vertically shrunk**: it clipped `currentDestinationView`, whose frame is **safe-area-inset**, so the rounded card stopped below the status bar and above the home indicator, and its top/bottom edges showed with the menu peeking through. User verbatim: *"now it is still shriking becuase the upper edge of the middle panel is shown, as well as the bottom edge. i want exactly just horizontally move right."* **Fix: the body is now a layered `ZStack`** — (1) `drawerPanel` full-bleed behind; (2) a **full-height `Color(.systemBackground)` SURFACE** in its own `GeometryReader { … }.ignoresSafeArea()` that carries the clip + shadow + offset, so the *card* spans the WHOLE screen height; (3) `currentDestinationView` on top, **un-clipped and keeping its own safe area** (NavigationStack / toolbar / hamburger stay below the status bar), slid by the same `peekWidth*0.55`. The content is inset from the surface's rounded corners so it never needs clipping; its off-screen-right part is clipped by the window. **Don't fold the surface back into a `.clipShape` on `currentDestinationView`** — that re-introduces the vertical shrink.

> **2026-06-05 follow-up #3 (full height + bigger corners — NOT an inset).** Full height (#2) hid the rounded corners at the screen edges, so a first attempt added a symmetric top/bottom inset to reveal them. The user rejected that hard — *"上下不要有edges"* (no top/bottom edges) — and asked instead for *"corners more rounded."* **Final:** the card stays **full-height, edge-to-edge (NO inset, no top/bottom margins)**, and the **leading-corner radius is enlarged to `peekCornerRadius = 50`** (was 30) so the top-left + bottom-left corners read as a rounded card even though they sit at the screen's top/bottom edges. The **surface** is `RoundedRectangle(cornerRadius: open ? peekCornerRadius : 0).fill(Color(.systemBackground))` (**no `.padding`**); the **content** mask is `RoundedRectangle(cornerRadius: open ? peekCornerRadius : 0).ignoresSafeArea()` (**no `.padding`**) — same shape, so the content (incl. the bottom composer) is clipped to the card and nothing pokes past the corner. **Don't add a vertical inset to make the corners show** — bump `peekCornerRadius` instead.

### Implementation (current — DrawerShell)

- `ContentView` (in [Nutritionist/ContentView.swift](Nutritionist/ContentView.swift)) holds `@State selectedTab: Int`, **`@State isDrawerOpen`** (DEBUG `-UITestDrawer` opens it on launch), `@State peekWidth` (full screen width from the **card-surface `GeometryReader`**, drives the slide offset), and `let peekCornerRadius` (the leading-corner radius, 50 — see follow-up #3; the card is full-height with NO inset).
- The body is a **layered `ZStack(alignment: .topLeading)`** (NOT a `clipShape` on `currentDestinationView` — see the 2026-06-05 follow-up #2 above), back-to-front:
  1. **`drawerPanel`** — `.ignoresSafeArea()` + `.opacity(open ? 1 : 0)` (**hidden when closed** so its footer doesn't bleed through the home-indicator strip) + `.offset(x: open ? 0 : -12)`. The nav panel revealed behind.
  2. **Card surface** — `GeometryReader { RoundedRectangle…fill… }.ignoresSafeArea()`: a **full-height** system-background slab (NO inset). Sets `peekWidth` from `proxy.size.width`. The transform, in this **exact order — round + shadow BEFORE offset**: `RoundedRectangle(cornerRadius: open ? peekCornerRadius : 0, style: .continuous).fill(Color(.systemBackground))` → `.shadow(.black.opacity(open ? 0.22 : 0), radius: 22, x: -14)` → `.offset(x: open ? proxy.size.width*0.55 : 0)`. **The order is load-bearing:** `.offset` is layout-neutral, so rounding *after* it would round the **device's right edge** instead of the card's **leading (left) edge** (the rejected "corner on the right side" bug). **No inset, no `.scaleEffect`, no scrim / `.saturation`.**
  3. **`currentDestinationView`** (a `@ViewBuilder` switch on `selectedTab`) — `.overlay(.topLeading) { hamburgerButton }` (toggles `isDrawerOpen`) + `.overlay { if open { invisible tap-to-close catcher } }` + **`.mask { RoundedRectangle(cornerRadius: open ? peekCornerRadius : 0).ignoresSafeArea() }`** (clips the content to the **same** full-height card shape as the surface so the bottom composer can't poke past the corner — `.mask` is visual-only, so the toolbar / safe area survive) + `.offset(x: open ? peekWidth*0.55 : 0)`. Keeps its own safe area; rides on the surface.
- `.animation(spring(0.46, 0.82), value: isDrawerOpen)` on the `ZStack` (eased when Reduce Motion).
- **`drawerPanel`** — **adapts to the color scheme** via the `drawerIsDark` / `drawer*Color` helpers (in [Nutritionist/ContentView.swift](Nutritionist/ContentView.swift)): a `LinearGradient` panel (warm-dark `#3c3630 → #2b2620` in dark mode · `nutritionistRice` in light), the nav list (`drawerRow` per `navigationMenuEntries`), and a "v3.0 · synced with Apple Health" footer. Title/subtitle/chip/footer colors all switch on `drawerIsDark` (cream-on-dark vs ink-on-cream). **`drawerIsDark` is derived from `appSettings.preferredColorScheme`** (only "system" falls back to `@Environment(\.colorScheme)` — because ContentView itself sets `.preferredColorScheme`, reading the environment alone is unreliable). Content padded `.trailing 84` to clear the peeked-screen sliver. **No identity row** (the logo/globe + "Nutritionist" title + "AI nutrition assistant" subtitle were removed 2026-06-09 per user request).
- **`drawerRow`**: icon chip (accent fill when active, else `drawerChipColor` — oat in light / white 8 % in dark) + title + subtitle; the active row gets an accent rounded background (`drawerActiveRowColor`: 16 % light / 30 % dark). Inactive icon/title/subtitle use the adaptive `drawer*Color` helpers. Tapping sets `selectedTab` and closes the drawer.

### Hamburger Button — Liquid Glass (iOS 26)

Unchanged styling — the project's `LiquidGlassCircleModifier` (tint 0.12, border 0.28, shadow 0.08), at 12 pt leading + 8 pt top. It now **toggles `isDrawerOpen`** (was a `Menu`). User verbatim (2026-05-20): "the side panel button need to be a liquid glass button io 26." Don't replace the label with a flat fill; don't drop the shadow to 0.

### Drawer Destinations

`navigationMenuEntries` lists five destinations (each with a `subtitle`), in this order: **Today** (`house`, t0) · **Calendar** (`calendar`, t1) · **Trends** (`chart.line.uptrend.xyaxis`, t3) · **Library** (`books.vertical`, t5) · **Settings** (`gear`, t4). **AI Chat is NOT a drawer destination** — it's presented as a blurred overlay from the chat bar (see "AI Chat Overlay" section). The active row is highlighted (accent chip + tinted background). **All five are real destinations — don't mark Trends/Library "Soon"** (the JS prototype did; this app ships them).

### Explicitly NOT Allowed

- **No bottom tab bar.** Don't reintroduce `TabView`, `.tabItem`, or any `UITabBarController`-backed accessor. The old `TabBarControllerAccessor` / `CalendarTabReselectionObserver` plumbing is dead and must not be revived.
- **Don't drop the panel `opacity(isDrawerOpen ? 1 : 0)`** — the footer bleeds through the bottom strip without it.
- **Don't add a dim/scrim or desaturation layer over the peeked screen.** The only overlay is the invisible tap-catcher. A `nutritionistRice` 0.62 scrim + `.saturation(0.18)` had crept in and washed the peeked screen into a grey/dead-looking card — the user rejected this **2026-06-05** as *"definitely problematic"* and asked for the crisp Claude-app look. The peeked screen stays **full-color**; depth comes from the left shadow + the 30 pt corner only.
- **Don't hardcode the drawer panel to a single tone.** It must adapt (warm-dark in dark mode, cream in light) so it matches the peeked screen — see the 2026-06-05 note. The app **defaults to dark**, so a hardcoded-cream panel is wrong for most users.

### Known limitation — destination state is not kept alive

*Flagged 2026-05-31 (Codex); severity re-assessed + draft fix applied same day.* `currentDestinationView` is a `switch` on `selectedTab`, so switching destinations **deallocates the previous one** (unlike the old `TabView`). Actual impact is narrow, not "lost replies": `AIChatView` sends via detached `Task {}` blocks that insert the AI `ChatMessage` into the shared `modelContext`, so **the reply persists and reappears via `@Query`** on return; and `sendMessage()` clears the draft on send. So the only real loss was an **unsent, half-typed draft** when navigating away mid-typing.
- **Fixed:** `AIChatView.messageText` is now `@SceneStorage("aiChatDraftText")` (not `@State`), so the unsent draft survives view recreation. Low-risk, no layout change.
- **Still resets (accepted):** the live `isProcessing` spinner — on return the persisted reply is already shown, so this is harmless.
- If a future need requires fully keeping the chat view alive, **don't reintroduce `TabView`** — keep `AIChatView` alive in a `ZStack` with visibility toggling, or hoist its request state into a shared model. Confirm first; an always-present `NavigationStack`+composer risks keyboard/layout quirks that can't be verified headlessly.

### Explicitly NOT Allowed (continued)

- **No top-bar navigation chrome that competes with the hamburger.** The hamburger overlay sits at `.topLeading` of every destination; **don't put a `ToolbarItem(placement: .navigationBarLeading)` in any child view** — it renders *underneath* the hamburger. This actually happened: CalendarView's "Today" button was on `.navigationBarLeading` and only its tail ("y") peeked out from behind the hamburger. Fixed 2026-05-26 by moving "Today" to `.navigationBarTrailing` (beside "Select"), which also matches the design (`screens.jsx` puts "Today" on the right). Put any per-screen leading action on the trailing side instead.
