# Elegant-Architecture Reference — Target Conventions vs Current State

*Established: 2026-06-03 (research-backed). This section is **aspirational guidance**, not a description of how the app works today. It records the idiomatic iOS-26 conventions to migrate toward when touching each area, and flags where the current code diverges. Don't treat these as "already done" — the rest of CLAUDE.md describes actual current behavior; this is the north star. The user's standing note: the app "works but isn't elegant."*

> Sourcing: synthesized from a deep-research pass (Apple docs/WWDC25, Point-Free, Swift by Sundell, Hacking with Swift, NSHipster, AzamSharp, Dimillian, OpenAI/OpenRouter/Gemini docs). Key source URLs are listed at the end of this section. Treat single-blog claims as "consensus, verify against Apple docs before a big refactor."

### 1. Architecture & state management (iOS 26)
- **Do: the "MV" pattern — views observe models directly; ViewModels are not required in SwiftUI** and are frequently an anti-pattern. Start with model + view; add a ViewModel only when a specific view has genuinely complex, view-only presentation logic. (Dimillian "Forget MVVM", Manferdini, AzamSharp.)
- **Do: use `@Observable` (Observation framework, iOS 17+), not `ObservableObject`/`@Published`.** `@Observable` redraws a view only when the *specific properties that view's body reads* change (granular invalidation → fewer redraws); `ObservableObject` redraws on any `@Published` change. Own an `@Observable` with `@State` (NOT `@StateObject`), share with `@Environment` + `@Bindable`. `@Observable` is class-only.
- **Do: keep business/network logic out of views** — put it in stateless services (an "Interactor"/service operating on shared state — nalexn Clean Architecture) or, for SwiftData-centric apps, in the `@Model` + feature-organized views (AzamSharp). Inject dependencies via protocols (or Point-Free `swift-dependencies` / `@Environment`), not hard singletons.
- **Current divergence:** `ContentView.swift` is a ~4000-line god-object with networking + business logic inline; `AIManager` is `ObservableObject`; `AppSettings.shared` is a global singleton. **Target:** split `ContentView` per feature/destination; migrate `AIManager` → `@Observable` and inject it; lift networking into an `AIService` (see §3). Migrating `AppSettings.shared` is high-blast-radius — do it last, behind the same API.
- **Caveats:** `@Observable` requires `@State` (using `@StateObject` silently misbehaves); a `switch`-based destination view destroys `@State` on navigation (our nav) — state that must survive needs `@SceneStorage` or a hoisted shared model (we already did this for the chat draft).

### 2. SwiftData conventions
- **Do: store typed value types, not hand-rolled JSON strings.** Any `Codable` struct/enum is a valid `@Model` attribute and SwiftData stores it *inline* in the row. So the AI nutrition payload is more idiomatic as a `Codable` `NutritionResponse` attribute than as a `String` of JSON. (Hacking with Swift, swiftyplace.) Use `@Relationship` for real entity graphs; reserve JSON-in-column for genuinely opaque blobs.
- **Do: ship a `VersionedSchema` from v1 and a `SchemaMigrationPlan`** — `.lightweight` for additive changes (new model/optional property w/ default), `.custom` (with `willMigrate`/`didMigrate`, manual `context.save()`) for transforms like de-dup before adding a uniqueness constraint. iOS 26 adds `@Model` class inheritance (gate `@available(iOS 26, *)`); use it only for true `is-a` hierarchies with deep (parent-type) queries — otherwise a discriminator property is better.
- **Do: use `@Query` directly in views** (treat the view as the VM); rely on autosave but wrap user-observable writes in explicit `save()` + `do/catch` (we already follow this — see "SwiftData Save Failures").
- **Preferences placement:** small values → `@AppStorage`/UserDefaults; per-scene UI state → `@SceneStorage`; real app data → SwiftData. Our `pinnedNutrientsJSON`/`excludedDateKeysJSON` JSON-in-`@AppStorage` is acceptable for small ordered lists.
- **Current divergence / risk:** nutrition stored as a JSON `String` (works, but a typed attribute would be queryable + safer); **no `VersionedSchema` yet**, and `NutritionistApp.init` *deletes the store on migration failure* — that's data-loss-on-upgrade waiting to happen. **Target:** introduce a `VersionedSchema` before the next model change. **Caveat:** touching a deleted `@Model` crashes hard — never hold stale references.

### 3. Multi-provider LLM client (directly relevant to the in-progress feature)
- **Do: one protocol-based abstraction.** Define an `LLMProvider` protocol; conform a `GeminiProvider` (native API) and a single `OpenAICompatibleProvider` reused for **both OpenRouter and Z.AI/GLM** (both expose OpenAI-style `/chat/completions`). Switching model/provider should be changing the `model` string + base URL + key, not new request/response code. (Natasha the Robot, daniloab.)
- **Do: use native structured-output, per provider.** OpenAI-compatible: `response_format: {type:"json_schema", json_schema:{strict:true, schema:…}}` — `strict:true` guarantees schema adherence (no parse-and-retry). Gemini: `generationConfig` with `responseMimeType:"application/json"` + `responseSchema` (its OWN shape, *not* the OpenAI one). Only a JSON-Schema subset is supported and unsupported keywords are silently ignored, so author the nutrition schema against the subset.
- **Do: always validate parsed values.** Structured output guarantees valid JSON/shape, **not** sane values — keep clamping calories/macros after decode.
- **Do: a reusable async retry with exponential backoff + jitter** (e.g. `Task.retrying(maxRetryCount:retryDelay:)` looping with `Task.sleep`; Swift by Sundell). Retry transient/5xx/429 only; never retry 4xx except 429. Chat completions are side-effect-free, so the **retry button is safe to re-send the same request** — preserve the last request payload and re-issue it (don't make the user retype).
- **Do: cancellation** — `URLSession.data` only checks cancellation *before* the call; call `Task.checkCancellation()` after it returns. Put networking in an `actor`. Surface errors to the UI (not silent `try?`).
- **Current divergence:** Gemini-only, manual `Task{}` in the view, no provider abstraction, no retry. **Target:** `AIService` actor + `LLMProvider` protocol + retry affordance. (Key plumbing for OpenRouter/GLM keys already added to Info.plist + Secrets.xcconfig.)

### 4. iOS 26 Liquid Glass
- **Do: use the native APIs** — `.glassEffect(.regular, in:)` (variants `.regular`/`.clear`/`.identity`, `.tint`, `.interactive()`), `.buttonStyle(.glass)` (secondary) / `.glassProminent` (primary), `.glassEffectID(_:in:)` + `@Namespace` for morph transitions, and **`GlassEffectContainer` to group nearby glass** (glass can't sample other glass; the container gives shared sampling + better perf and the droplet-morph blend).
- **Do: glass on the navigation/floating layer only** — never on content (lists, tables, media). Tint must be **semantic** (CTA/state), not decoration; text on glass auto-receives a vibrant treatment.
- **Do: accessibility** — read `@Environment(\.accessibilityReduceTransparency)` and switch to the `.identity` variant when on (`.glassEffect(reduceTransparency ? .identity : .regular)`); keep the existing `reduceMotion` handling.
- **Current divergence:** the app hand-rolls `LiquidGlass*` modifiers (`.ultraThinMaterial` + overlays). **Target:** on iOS 26, the shared modifiers should wrap the native `.glassEffect`/`GlassEffectContainer`; keep the hand-rolled stack only as the pre-26 fallback. This refines (doesn't replace) the existing "Always Refer to the iOS 26 Design Guide" rule with concrete API names.

### 5. Concurrency & secrets
- **Concurrency — Do:** SwiftUI `View` is `@MainActor`-isolated, so a `Task{}` started in a view inherits the main actor (UI-safe); prefer `Task` over `Task.detached`. For async tied to a view's lifecycle, prefer **`.task(id:)`** (auto-cancels on id change / disappear) over a manual `Task{}` you have to cancel yourself. Keep callback `Task`s thin — just inform the model; do heavy/shared-state work in an `actor`. Our `Task{}` + `@MainActor.run` works but `.task(id:)` + an `AIService` actor is the cleaner target.
- **Secrets — Do:** understand that **xcconfig/Info.plist only keeps keys out of git, NOT out of the shipped binary** — anyone can unzip the `.ipa` and read the plist. For user-supplied keys (OpenRouter/GLM), store at runtime in the **Keychain** (not Info.plist); ideally don't ship secrets at all (backend with revocable tokens). For a personal/sideloaded build the Info.plist+xcconfig approach is a pragmatic trade-off, but **document that the Gemini key is extractable** and prefer Keychain + in-app entry for the new provider keys.

### Verification & corrections (2026-06-03 adversarial pass)
The conventions above were re-checked by a 3-vote adversarial research pass: **23 of 25 sampled claims confirmed** (mostly 3-0), 2 refuted. Refinements + things that were **refuted (do NOT do)**:

- **Structured output does NOT remove the need to validate values** (refuted 0-3). It guarantees JSON *shape*, never that calories/macros are sane. Our pinned-nutrient totals + trends sum these, so a schema-valid-but-absurd value would propagate — keep clamping after decode.
- **Gemini is NOT OpenAI `response_format`** (refuted 0-3). Gemini uses `generationConfig.responseMimeType:"application/json"` + `responseSchema` (its own shape); the OpenAI-compatible providers use `response_format`. Keep the two request bodies distinct (we do).
- **Gemini's JSON-Schema subset GREW in Nov 2025** (now includes `anyOf`/`$ref`/`$defs`/`additionalProperties`/`minItems`/`maxItems`/`format`/`enum`/`minimum`/`maximum`). Don't over-restrict the nutrition schema to the old "7 types only" framing — but unsupported keywords are still *silently ignored*, so verify against live docs.
- **Native glass auto-adapts to Reduce Transparency / Reduce Motion; hand-rolled glass does NOT.** Our `LiquidGlass*` modifiers + the Canvas water-washed texture must be **manually tested + given fallbacks** under those settings (the system won't do it for custom elements).
- **`GlassEffectContainer` exists because glass can't sample other glass** — group nearby glass in a container for shared sampling + perf + morphing; don't scatter independent `glassEffect`s.
- Source caveat: Apple's WWDC25 transcripts (sessions 266, 291) are JS-rendered and weren't first-party-scrapable; their verbatim quotes rest on multiple independent corroborating sources — high-confidence-via-corroboration, not first-party-verified.

### Open questions for the elegant migration (verified as unresolved)
1. **Water-washed texture vs Liquid Glass:** Apple says glass on the navigation layer only, never content. The brand water-washed Canvas strip is *content/decoration* — should it stay non-glass, and should the `LiquidGlass*` modifiers wrap native `.glassEffect()` behind `if #available(iOS 26,*)` with the `.ultraThinMaterial` stack as the pre-26 fallback?
2. **Per-model structured-output:** which OpenRouter/GLM models actually support `json_schema` + `strict:true` vs only `json_object` (what we use now) — feature-detect per model, or keep the uniform `json_object` + schema-in-prompt for portability?
3. **Nutrition `String` → typed `Codable` `@Model` attribute:** needs a custom `VersionedSchema` migration (decode-and-rewrite in `willMigrate`), and a safe replacement for `NutritionistApp`'s current *delete-the-store-on-migration-failure* behavior (data-loss risk).
4. **Keychain for user-supplied OpenRouter/GLM keys:** the access pattern, rotation/revocation story, and whether a minimal backend proxy is warranted — not yet designed.

Vote = (confirm−refute) across 3 skeptic verifiers.*

**Architecture & concurrency**

- **F1 — SwiftUI concurrency / "state-as-a-bridge" (high; 3-0, the @MainActor-default sub-claim 2-1).** The `View` protocol is `@MainActor`-isolated by default (Swift 6 / Xcode 16, SE-0401), so a model instantiated inside a view's declaration is automatically main-actor-isolated with no explicit annotation. Recommended architecture: **separate async/non-UI logic from view logic using a piece of `@State` as a bridge** — state initiates the async task; when async work finishes it performs a *synchronous* mutation on state so the UI updates reactively. SwiftUI action callbacks are synchronous by design; launch a `Task` for async work but **keep that Task thin — "it's there to inform the model about a UI event."** This is the idiomatic replacement for the app's manual `Task{}` + `@MainActor.run` blocks and inline networking. Source: WWDC25 session 266 "Explore concurrency in SwiftUI" (verbatim: "@MainActor is SwiftUI's compile-time default… It's safe automatically"; "You can use a piece of state as a bridge… perform a synchronous mutation on the state, so that your UI can update as reactions to this change"; "try to keep the code in this async context simple. It's there to inform the model about a UI event"). Dissent (2-1) raised only an isolation-direction nuance that doesn't contradict isolation flowing down from the `@MainActor` view to a locally-instantiated model.

- **F2 — Dependency injection over a global singleton (high; 3-0).** Propagate dependencies through `@Environment`-style mechanisms, not a global like `AppSettings.shared`. Point-Free's **swift-dependencies** is the prevailing library: modeled on SwiftUI's Environment, dependencies are declared/read via a `@Dependency` property wrapper over a `DependencyValues` registry (key-path access mirroring `EnvironmentValues`, e.g. `@Dependency(\.continuousClock) var clock`). It works **inside `@Observable` model classes** by marking the property `@ObservationIgnored` (`@ObservationIgnored @Dependency(\.date.now) var now`) — safe because dependencies don't need to be observed (works around a historical compiler bug with bare `@Dependency` in `@Observable`). README framing: "more ergonomic than explicitly passing them around everywhere, but safer than having a global dependency." Source: github.com/pointfreeco/swift-dependencies.

**SwiftData**

- **F3 — `@Model` inheritance is iOS-26-only and for true is-a only (high; 3-0).** New in iOS 26; gate with `@available(iOS 26, *)` on the subclass, its `VersionedSchema`, AND its migration stages. Use inheritance **only for a natural "is-a" hierarchy** — sharing a single common property (e.g. `name`) across unrelated models should be a **protocol**, not a superclass. Inheritance pays off only with **deep searches** across the parent type; if queries only ever fetch leaf subclass types ("shallow search"), **flatten the models and use a discriminating property** instead of subclassing. Source: WWDC25 session 291 "SwiftData: Dive into inheritance and schema migration" (verbatim: "inheritance should not be harnessed to share common characteristics among models… better expressed as a protocol conformance"; "if your queries or fetches only ever fetch the leaf class types… we would consider flattening our models"). Apple's true sweet spot is *mixed* deep+shallow queries.

- **F4 — Schema migration: `SchemaMigrationPlan` + lightweight/custom stages (high; 3-0).** Migrations are a `SchemaMigrationPlan` of stages: `MigrationStage.lightweight` (automatic — additive changes, adding subclasses) or `MigrationStage.custom` (`willMigrate`/`didMigrate` closures for data transforms like de-dup, with a manual `context.save()`); attach via `ModelContainer(for:migrationPlan:configurations:)`. **Adding a uniqueness constraint is lightweight ONLY if no duplicates exist** — if duplicates exist you must do a custom migration that de-dupes in `willMigrate` before the constraint applies, or **the container fails to load and the app crashes on launch**. Purely additive lightweight changes can be inferred (explicit plan optional). This is the documented thing to introduce *before the app's next model change* — the app currently has **no `VersionedSchema` and deletes the store on migration failure (data-loss on upgrade)**. Sources: WWDC25/291; hackingwithswift.com complex-migration guide (traced to Apple's WWDC23 SampleTrips `migrateV1toV2` pattern).

**Multi-provider LLM client**

- **F5 — OpenAI-compatible Structured Outputs need `strict: true` (high; 3-0).** For OpenRouter and Z.AI/GLM, enable Structured Outputs via `response_format: {type:"json_schema", json_schema:{strict:true, schema:…}}` on Chat Completions. **`strict:true` is required for the schema-adherence guarantee** (constrained decoding), as distinct from plain JSON mode (valid JSON, no schema guarantee). `strict` defaults to false and a `json_schema` block is still accepted without it — it just won't be *enforced*. The app currently uses the lower-common-denominator `response_format:{type:"json_object"}` + schema-in-prompt; **upgrading to per-provider `json_schema`+`strict:true` where supported is the stronger target.** Source: developers.openai.com structured-outputs guide.

- **F6 — Gemini uses its OWN structured-output shape + a silently-ignored subset (high; 2-1).** Gemini's native path is `generationConfig.responseMimeType:"application/json"` + `responseSchema` — **NOT** the OpenAI `response_format` (keep the two request bodies distinct). It supports only a **subset** of JSON Schema and **silently ignores unsupported properties** ("The model ignores unsupported properties"). The subset **grew in Nov 2025** to add `anyOf`/`$ref`/`$defs`/`additionalProperties`/`minItems`/`maxItems`/`format`/`enum`/`minimum`/`maximum` — so don't over-restrict to the old "7 types only" framing, but re-check live docs. (The one GitHub 400 on `additionalProperties` is a client-SDK bug, not API rejection.) Source: ai.google.dev/gemini-api/docs/structured-output.

- **F7 — Structured output guarantees shape, NEVER values — always validate (high; 3-0).** Constrained decoding guarantees syntactically valid JSON matching the schema's *shape*, **not** that the numbers are sane ("perfectly valid JSON and completely wrong"). Always validate parsed values before use. Directly load-bearing here: AI nutrition is stored as JSON and summed into **pinned-nutrient totals + trends**, where a schema-valid but absurd/negative value would propagate unchecked — keep clamping after decode; never a silent `try?` parse path. Edge case that reinforces it: `finish_reason:"length"` (hit `max_tokens`) yields truncated invalid JSON, so even the syntactic guarantee only holds on normal completion. Sources: Gemini docs ("it does not guarantee the values are semantically correct… Always validate the final output"); OpenAI docs.

**iOS 26 Liquid Glass**

- **F8 — `glassEffect(_:in:)` + `.glass`/`.glassProminent` are the official API (high; 3-0).** Standard SwiftUI/UIKit components (bars, sheets, popovers, controls) adopt Liquid Glass **automatically when recompiled against the iOS 26 SDK**; **custom views do NOT auto-adopt** — use `.glassEffect(_:in:)` (and `.buttonStyle(.glass)` / `.glassProminent`). Lean on system frameworks + `glassEffect` rather than hand-rolling `.ultraThinMaterial` + overlay + shadow. App target: the shared `LiquidGlass*` modifiers should *wrap* native `.glassEffect` on iOS 26 and keep the hand-rolled stack only as the pre-26 fallback. Sources: Apple "Applying Liquid Glass to custom views" ("Standard components in SwiftUI use Liquid Glass"; "Renders a shape anchored behind a view with the Liquid Glass material"); "Adopting Liquid Glass."

- **F9 — Group glass in a `GlassEffectContainer` (high; 3-0).** "A view that combines multiple Liquid Glass shapes into a single shape that can morph individual shapes into one another." **Glass cannot sample other glass**, so the container provides a shared sampling region → better rendering performance + blend/morph between elements. Use it whenever multiple glass views are near each other (a single isolated glass element needs none); morph transitions additionally need `glassEffectID(_:in:)` + a `@Namespace`. An adversarial search for a "performance myth" found zero disputing sources. Sources: Apple GlassEffectContainer docs; "Applying Liquid Glass to custom views."

- **F10 — Use glass sparingly, navigation layer only (high; 3-0).** Apple: "Creating too many Liquid Glass effect containers and applying too many effects to views outside of containers can degrade performance. Limit the use of Liquid Glass effects onscreen at the same time." And on UX: "If you apply Liquid Glass effects to a custom control, do so sparingly… overusing this material in multiple custom controls can provide a subpar user experience by distracting from [the content]. Limit these effects to the most important functional elements." So: glass on the **navigation/floating layer** (toolbars, tab bars, floating buttons), **never on content** (lists, tables, media). Mechanism: each glass effect needs ~3 offscreen textures; the container consolidates to one render pass. Bears directly on the app hand-rolling `LiquidGlass*` everywhere. Sources: Apple "Adopting Liquid Glass"; "Applying Liquid Glass to custom views."

- **F11 — Native glass auto-adapts to accessibility; custom glass does NOT (high; 3-0).** Reduce Transparency / Reduce Motion are honored automatically for standard components and the native `.glassEffect()` API, but **custom elements must be explicitly tested and given fallbacks** — the system won't adapt them. Apple: "If you use standard components from system frameworks, this experience adapts automatically. Ensure you test your app's custom elements, colors, and animations with different configurations of these settings." The app's hand-rolled `.ultraThinMaterial` + Canvas water-washed texture are custom elements → need manual fallbacks (target: `.glassEffect(reduceTransparency ? .identity : .regular)` on iOS 26 + keep the existing `reduceMotion` handling). Source: Apple "Adopting Liquid Glass" (corroborated verbatim by LogRocket).
